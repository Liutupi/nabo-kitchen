# KRC1 流式读取实验

这个独立宿主实验用于探索未来更大菜库的索引读取，**尚未接入固件、构建门禁、界面、存储或工牌**，也没有制作一千道真实菜谱。测试中的 1000 和 1500 条数据仅复制现有菜谱正文并赋予合成 ID，用于检查规模和边界。

`ksc_open()` 用现有的 `krc_open()` 校验 KRC1 容器，在不分配或复制整个字典的情况下定位 `ids` 数组。`ksc_next()` 逐条读取稳定 ID 与对应的 16 字节索引；`ksc_page()` 用调用方限定的缓冲区分页，可按菜类或**主料**筛选，并在多次调用间保存游标；`ksc_find_id()` 线性查找完整 ID，并拒绝目标 hash 对应多条记录的歧义；`ksc_body()` 使用现有受限解压器按需读取一道菜的正文。调用期间输入数据必须保持有效，未来接入时可以考虑使用 Flash 映射的数据。

筛选只读取 KRC 索引里的主料位图，**不是**完整食材忌口、过敏原、调料、搜索或推荐实现。字典扫描器针对现有打包器生成的规范格式，不能作为通用 JSON 校验器。打开时校验 KRC1 的 CRC 和结构边界；读取每个 ID 时校验其与索引 hash 的对应关系；解压正文时校验该正文 CRC。查找会扫描并校验整份 ID 列表，拒绝与目标 hash 相同的重复项。完整数据和 schema 校验及 hash 碰撞检查仍须在打包时完成；不能直接把不可信或只部分校验的数据用于生产。

## 重现宿主测试

测试需要独立维护的 `nabo-kitchen` 源码目录及其 Python 依赖（`heatshrink2`、`jsonschema` 等）；可用 `NABO_RECIPE_ROOT` 覆盖默认的同级目录。本次本机运行方式：

```sh
NABO_RECIPE_ROOT=/Volumes/NABO-Build-20261004/nabo-kitchen \
PYTHONDONTWRITEBYTECODE=1 \
/Users/tupi/Library/Caches/nabo-kitchen-fw/venv/bin/python \
experiments/krc_stream/test_krc_stream.py
```

四项宿主测试覆盖当前实际菜库和按真实 KRC1 格式生成的 1000、1500 条合成数据：不同大小分页、按主料及菜类筛选、63/64、127/128 等稳定 ID 边界、按需正文解压、截断和损坏，以及重新封装 CRC 的重复 ID。当前两组合成包分别为 726,677 和 1,088,805 字节；大小随实际正文及字典变化，不能用于保证真实菜库的容量。

## 本次内存观察和限制

使用 ESP32-C3 `riscv32-esp-elf-gcc` 14.2.0 交叉编译时，`ksc_cursor` 为 **48 字节**，调用方提供的 8 行 `ksc_row` 缓冲为 **448 字节**；1000 与 1500 条数据不改变这两个结构的大小。如果调用方另提供完整的 2048 字节正文缓冲，三者合计为 2544 字节。实验本身不做堆分配，但 Flash 映射、应用状态、编译器栈、中断及固件其他内存都需另计。

使用 `-O2 -fstack-usage` 时，编译器报告 `ksc_open`、`ksc_next`、`ksc_page`、`ksc_find_id` 各自静态栈帧分别为 80、112、144、192 字节；调用链和外部调用者的栈帧需要叠加。单独对象文件在最终链接之前的代码段为 2214 字节。这些只是编译器观察，**不是实机内存实测或整体栈容量保证**。

初始化会校验整包 CRC 并遍历正文边界；ID 查找是线性扫描，目前每次还会重复容器校验。实际 ESP32-C3 的响应时间、启动耗时、Flash 映射开销、栈高水位和堆余量均未测试。真正的千道菜产品还需要有界的菜名/元数据读取、更宽或分页的界面状态、完整食材过滤、可协作的推荐搜索、兼容旧数据的事务式存储迁移、真实内容及美术预算，以及实机验收。
