# KRC1 streaming experiment

This isolated host experiment explores catalog indexing for a future larger kitchen. It is **not connected to the firmware, build gate, UI, storage or device**, and does not create a thousand real recipes. The 1,000- and 1,500-entry test packs clone existing recipe bodies with synthetic IDs solely to exercise scale and boundaries.

`ksc_open()` validates the existing KRC1 container using the production `krc_open()` and finds the `ids` array in its dictionary without allocating or copying that dictionary. `ksc_next()` streams stable ID strings and their corresponding 16-byte index records. `ksc_page()` emits a caller-bounded page with optional course or **main ingredient** filters, advancing a cursor across calls. `ksc_find_id()` is a linear, full-ID lookup that rejects ambiguous matching hashes. `ksc_body()` uses the existing bounded decompressor for one requested recipe. The input buffer must remain valid for the whole cursor lifetime; it can be a flash-mapped pack in a future integration.

The filter only examines the KRC index's main-ingredient bitmap. It is **not** a full ingredient exclusion, allergy, seasoning, search or recommendation implementation. This dictionary scanner is restricted to the canonical format generated by the existing packer, not a general-purpose JSON validator. On open, KRC1 CRC and structural bounds are checked; each ID/hash pair is checked as it is consumed, and each body CRC is checked when decoded. Lookup scans and validates the entire ID list and rejects duplicates with the requested hash. Complete source/schema validation and hash-collision checks must still happen at pack time; untrusted or partially validated data are not suitable for production.

## Repeatable host test

The test needs the separately maintained `nabo-kitchen` source tree and its Python dependencies (`heatshrink2`, `jsonschema` and their dependencies). `NABO_RECIPE_ROOT` can override the default sibling directory. For the local environment used in this experiment:

```sh
NABO_RECIPE_ROOT=/Volumes/NABO-Build-20261004/nabo-kitchen \
PYTHONDONTWRITEBYTECODE=1 \
/Users/tupi/Library/Caches/nabo-kitchen-fw/venv/bin/python \
experiments/krc_stream/test_krc_stream.py
```

Four host tests cover the real currently packaged catalog and actual KRC1 packs generated with 1,000 and 1,500 synthetic entries: paging at multiple sizes, matching main ingredients and course bits, stable IDs at 63/64, 127/128 and later boundaries, per-recipe decompression, truncated/corrupt data, and a resealed duplicate-ID case. The current synthetic runs produced 726,677 and 1,088,805 bytes respectively; these sizes depend on the recipe bodies and source dictionary, and do not predict the size of a real collection.

## Observed memory and limits

With ESP32-C3 `riscv32-esp-elf-gcc` 14.2.0, `sizeof(ksc_cursor)` was **48 bytes** and eight caller-owned `ksc_row` values occupied **448 bytes**, regardless of whether the pack held 1,000 or 1,500 entries. A caller that also supplies a full 2,048-byte body buffer would reserve 2,544 bytes for those three objects. The experiment has no heap allocations of its own, but the pack mapping, application state, compiler stack, interrupts and other firmware memory are additional costs.

With `-O2 -fstack-usage` the compiler reported individual static frame sizes of 80 bytes for `ksc_open`, 112 for `ksc_next`, 144 for `ksc_page`, and 192 for `ksc_find_id`; their calls and caller frames add up. The standalone object was 2,214 text bytes before final linking. These are compiler observations, **not a device measurement or an overall stack guarantee**.

Initialization checks the full pack CRC and walks body extents; ID lookup is linear and currently repeats container validation. Runtime latency, startup time, flash mapping cost, stack high-water mark and heap headroom on the actual ESP32-C3 remain untested. A practical thousand-dish product still needs bounded title/metadata access, wider or paged UI state, full ingredient filtering, cooperative recommendation search, a compatible transactional storage migration, content and art budgets, and device acceptance.
